## B. The one thing to act on today: customer data is public

`github.com/akashshinde700/gmb` is a **public** repository, and its history —
not its current tree — still carries:

| Commit | Contains |
|---|---|
| `1a097a7d`, `f5d33d92`, `02b82c88`, `a6e0c209` | `db/custom.db` (~311–319 KB SQLite) |
| `8533c55f` … `a6e0c209` | `.env` |

The current `main` no longer tracks either file (`.gitignore` covers `/db/`,
`*.db`, `.env*`), and the current tree is clean. **Deleting a file in a new
commit does not remove it from history** — any of those commits can be fetched
from the GitHub API today. This was verified: the committed database was
downloaded and inspected. It contains 19 tables including **4 user rows with
scrypt password hashes**, 7 leads (names/phones/emails), 3 payments, 3
businesses and 703 analytics events. The `.env` blob held only `DATABASE_URL`,
so no API keys leaked — but the password hashes and the leads did.

This is not something a code change can fix. It is four commands and one
notification:

```bash
# 1. Purge the blobs and force-push (coordinate: everyone re-clones).
git clone --mirror https://github.com/akashshinde700/gmb.git gmb.git
cd gmb.git
git filter-repo --path db/custom.db --path .env --invert-paths
git push --force

# 2. Rotate the session secret that was live while that file was published.
openssl rand -hex 32   # → APP_SECRET on the server, then restart

# 3. Assume every password hash in that file is cracked or will be.
#    tokenVersion is already bumped by the reset flow (`/api/auth/forgot`
#    → `/api/auth/reset`), so a forced reset logs out every old session.
```

4. GitHub keeps unreachable objects available to anyone with the blob SHA, and
   forks keep their own copies, so treat steps 2 and 3 as already-due — and if
   any of those four accounts or seven leads belong to a real customer, they are
   owed a plain-language notice (India's DPDP Act treats lead PII as personal
   data; contracts usually require notice within 72 hours).

Prevention, since `.gitignore` only helps after the fact: `gitleaks` in CI, or a
pre-commit hook that refuses `*.db` and `.env*`. The repository also still has
`freemodels-api (1).json` in it — a byte-identical duplicate of
`freemodels-api.json`, i.e. a half-of-a-browser-download that was committed.
That one is deleted in this pass.

## C. Bugs found and fixed in this pass

### 1. Two metered allowances could be overspent (races)

**Where:** `src/app/api/ai/generate/route.ts`, `src/lib/appearance.ts`.

Both counters were read, compared and then written in a *separate* statement:

```ts
const used = periodExpired ? 0 : business.aiUsedCount;
if (allowance >= 0 && used >= allowance) throw new HttpError(..., 402);
await db.business.update({ ..., data: { aiUsedCount: { increment: 1 } } });
```

Two requests arriving together (two tabs, a retry, a double click) both read
`used = allowance - 1`, both pass the check and both increment. The customer
gets one generation more than the plan includes, and nothing is logged. The
design-change counter had the same shape, and `maxThemeChanges` is settable now
(see §4), so this went from theoretical to reachable.

The codebase already knew the right pattern — `billing.ts` claims a coupon with
a conditional `updateMany` and checks `count` — so both sites now do the same:
claim the unit with a single conditional statement (`aiUsedCount: { lt: allowance }`,
period rollover guarded on the `aiPeriodStart` that was read), re-read once if
the claim loses, and report the limit honestly if it is genuinely gone.

**Proved it, not just claimed it.** `tests/usage-race.mjs` (new) fires 6
simultaneous calls against an allowance of 2. Against the old code the design
change check accepted **3**; with the fix it accepts exactly 2 and refuses 4
with 402. Same numbers for AI generations.

### 2. A failed generation was charged to the customer

**Where:** `src/app/api/ai/generate/route.ts`.

The credit was claimed *before* calling the model. `generateJson()` returns
`null` whenever every configured provider fails — timeout, quota, unparseable
output — and the route then serves deterministic template copy and reports
`generated: false`. The customer was charged one of their monthly generations
for copy they could have had with no model configured at all. The credit is now
given back when the response is not model-written (best-effort: a failed refund
must not fail the response the customer is waiting for). `tests/usage-race.mjs`
covers this too, by making its stub model fail on demand: content is still
served, `generated` is `false`, and the meter reads 0 afterwards.

### 3. `npm run test:all` was broken

**Where:** `tests/section-editor.test.mts` → `src/lib/sections.ts`.

The suite imports app code that uses the `@/…` path alias. `tsc` and the
bundler resolve that from `tsconfig.json`; `node --experimental-strip-types`
does not, so the run died with `ERR_MODULE_NOT_FOUND: Cannot find package
'@/lib'` and every suite after it never ran — including the ones that would have
caught §1. This is why "68 unit tests pass" and "npm run test:all" could both be
true: the failing suite is the last of the `.mts` group, before the API suites.

Fixed with `tests/path-alias.mjs`, a 40-line Node resolution hook loaded with
`--import`, wired into `test:sections` and `test:all`. `section-editor` now runs
15 checks and the whole chain passes.

### 4. Plan limits the server enforces but nothing could set

**Where:** `src/app/api/admin/plans/*`, `src/lib/serialize.ts`,
`src/lib/types.ts`, admin Plans tab.

`maxThemeChanges` and `maxDomains` are read by `appearance-rules.ts` and
`domain-rules.ts`, are documented as "set by an admin", are written by the seed —
and were absent from the admin API and the admin plan form. So the metering was
unreachable: no plan could ever hit the 402 branch, and a bundled domain
allowance could only be changed by editing the database. Both fields are now
part of plan create/update, returned by the API, and editable in the form
(two number inputs, `-1` = unlimited, matching the existing style); the plan card
mentions them only when the plan actually meters them.

### 5. `tsx prisma/seed.ts` would happily create an admin with a known password

**Where:** `prisma/seed.ts`.

`process.env.ADMIN_PASSWORD || "admin1234"` — the fallback exists for local
seeding, but "local" was an assumption about the operator: a fresh deploy, a CI
job or a restored environment would create the platform admin (with
impersonation rights) using a password that is in this repository. Seeding with
`NODE_ENV=production` and no `ADMIN_PASSWORD` is now refused outright.

### 6. The onboarding draft outlived the session

**Where:** `src/lib/onboarding-draft.ts` (new), `src/store/app-store.ts`,
`onboarding-view.tsx`.

The wizard keeps a half-filled form in `localStorage` so a reload does not lose
it. That content is business PII — owner name, phone, email, address — in plain
text, and it survived sign-out on a shared computer. It is now cleared by both
sign-out paths. `sessionStorage` was the alternative and was rejected: it clears
itself, but it also throws the draft away on an accidental tab close, which is
the exact accident the draft exists for.

### 7. Two lint warnings that could not fire correctly

**Where:** `src/components/views/dashboard-view.tsx`.

`useFetch` took a caller-supplied `deps` array, handed it to `useCallback`, and
suppressed a rule (`react-hooks/use-memo`) that was not the one complaining —
so `npm run lint` printed two `exhaustive-deps` warnings forever. Every call
site passed `[]`, so the parameter was a promise the hook never had to keep: it
now reads `fn` through a ref, the two warnings are gone, and `npm run lint` is
clean. One documented exception remains for `set-state-in-effect`, with the
reason written next to it.

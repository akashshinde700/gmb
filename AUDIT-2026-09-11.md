## B. The bug found and fixed

### Admin customer list: capped at 100, search filtered in the browser

**Severity: P1 (latent).** No impact on the live system today. Certain breakage
at customer 101.

`GET /api/admin/customers` supports SQL search (`q`), paging (`take`/`skip`) and
reports a real `total`. The endpoint even carries a comment saying so:

> *"Search runs in SQL. Filtering the first 200 rows in JS meant a customer
> outside that window could not be found at all."*

The screen was never wired to any of it. It called the endpoint with no
parameters — which answers with at most **100 rows** — and the search box ran a
`.filter()` over whatever came back.

**Reproduced on this machine.** The local database holds 788 customer accounts
(accumulated Playwright signups):

```
GET /api/admin/customers        → rows 100   meta {"total":788,...}
```

The screen rendered `Showing 100 of 100 customers`. 688 accounts were invisible,
and searching for any of them returned *"No customers match your search"* — for
an account that exists and logs in fine.

Three further consequences of the same line:

- **Export CSV** wrote only the rows on screen. A spreadsheet that silently
  stops at 100 customers is worse than no export.
- **The count lied.** Not "showing a page" — it asserted 100 was the total.
- **No paging control existed**, so there was no way to reach row 101 at all.

**Fixed** by connecting the screen to the endpoint, matching the pattern already
used correctly by the customer-facing leads table (`leads-tab.tsx`):

- search runs in SQL, debounced 350 ms
- 50 rows per page with Previous / Next
- `Showing 1–50 of 788 customers` from the server's own count
- a request-id guard so results for `sha` cannot overwrite results for `sharma`
- Export CSV fetches every matching row (endpoint cap: 200) and says so when
  the match set is larger
- deleting the last row on a page steps back instead of stranding the admin

**Verified.** Four new tests in `e2e/06-admin.spec.ts`.

Three of them need more than one page of customers to say anything, and they
were run against the previous build (which contained the buggy code): **all
three failed**; against the fixed build **all three pass**.

Those three skip on a small database — which, after the dev-database cleanup
below, is most of the time. So a fourth test was added that runs at **any**
size: it watches the network and asserts that typing in the search box produces
a request carrying `q=` and `take=`. Qualified the hard way — the `q` parameter
was removed from the code, the app rebuilt, and the test **failed**; restored,
it passes. That is the guard that will still be working in a year.

## E. Recommendations, in the order I would do them

### P1 — done, same day

**`journal_mode = WAL` — enabled on live.** Readers no longer block on a write.

It could not be turned on as a one-liner, because of a dependency that had to be
fixed first. Both deploy scripts backed the database up with:

```
gzip -c $DB_FILE > dump.db.gz
```

That is a raw copy of the main file, taken **while the app is still serving**
(`deploy.py` backs up at step 2 and stops the app at step 3). Under
`journal_mode=delete` every committed transaction is already in that file, so
the copy is complete. Under WAL it is not — recent commits sit in `<db>-wal`
until a checkpoint.

Measured on the live server, with one row freshly written through the app:

```
live      rows=784
raw copy  rows=783   ← the old backup silently drops it
.backup   rows=784   ← the online backup API is complete
```

The raw copy opens cleanly and passes `integrity_check`. It is simply missing
the newest rows — a backup that looks fine until the day you restore it.
Enabling WAL without fixing this would have quietly degraded every backup taken
afterwards.

Both scripts now use `sqlite3 .backup` (SQLite's online backup API, correct in
either journal mode and consistent against a live writer), and `deploy-swap.py`
aborts the deploy if the backup fails. **This required editing `deploy.py`,
which is otherwise off-limits** — one block, at the user's instruction.
`8e9fabb2…` → `cfd18859…`.

Verified end to end on a real deploy: the backup it produced restores with
`integrity_check: ok`, 4 users and 784 events — matching live exactly.

**Deploy-time backups removed; replaced with an on-demand download.** By
instruction, neither deploy script backs the database up any more, and the 32
files on the server (2.7 MB, going back to 7 September) were deleted.

In their place: **Admin → Overview → Download backup**
(`GET /api/admin/backup`). It uses `VACUUM INTO`, which runs inside a
transaction and writes a complete, compacted database — the same guarantee
`sqlite3 .backup` gives, and the reason a raw file copy could not be used here
either, now that the database is in WAL mode.

Admin-only, 6 downloads per admin per hour, every download written to the audit
log, temp file deleted whether the download succeeds or fails. Verified against
the live server: 200, `application/gzip`, 91 KB compressed / 643 KB restored,
`SQLite format 3`, with the `User`, `Business` and `Payment` tables present.
A customer gets 403 and a signed-out visitor gets 401.

**The trade, stated plainly:** there is now no automatic safety net. A deploy or
a bug that loses data has nothing to roll back to except whatever was last
downloaded by hand. `--rollback` still restores the previous *build*, but that
is code, not rows. Take a download before anything risky.

**Local dev database cleaned.** 812 `@example.com` accounts from Playwright runs
deleted (no admins among them); the 4 real seeded users remain. 816 → 4 users,
616 → 3 businesses, payments untouched at 18.

## F. What I did NOT test — stated plainly

- **Screen readers.** No NVDA/JAWS/VoiceOver run. Label and structure checks are
  not a substitute.
- **Colour contrast.** Not measured against WCAG ratios.
- **Real payment flows.** Razorpay live keys are installed; I did not put a real
  card through. Webhook signature verification was read, not exercised.
- **Email and SMS delivery.** Disabled in the test environment on purpose.
- **Cross-browser.** Chromium only. No Safari or Firefox.
- **Load testing after the changes.** The throughput figures in
  `SCALE-AUDIT.md` are from 11 September and were not re-measured.
- **`tests/platform.mjs`.** Needs a `root@test.local` fixture this database does
  not have; it did not run.
